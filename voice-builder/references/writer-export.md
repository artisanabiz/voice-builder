# Export a standalone Writer

The deliverable is a usable skill that knows how to write without the Builder or its conversation. The default is directly authored Markdown; there is no compiler, Python runtime, record schema, sample quota, or mandatory benchmark.

## Settle the content and destination

After the user accepts the trial, show the lasting guidance to be retained, including exact signatures and their scope. Reuse prior approvals. A request for an earlier export permits a provisional version with unresolved limits identified. Approval of a draft alone does not settle unaddressed consequential choices.

Use the requested name and destination. If missing, propose a short name and a local deliverable destination in one practical choice; a delegated choice can be made and reported. Keep creation separate from global installation or publication. Preserve existing files; a new candidate folder is preferable to overwriting a working release without authorization.

## Write the skill

Create a folder with a `SKILL.md` containing YAML `name` and `description`. The name uses lowercase letters, digits, and hyphens. The description identifies the voice and its intended writing or review tasks, with a boundary that prevents unrelated work from acquiring this voice. Avoid claiming the reference voice is the user's identity.

Include what changes the Writer's decisions:

- The provenance label: own voice, reference voice, or deliberately selected blend; languages and formats represented.
- Concrete expression and development guidance derived from the accepted calibration, including what varies with the brief.
- Confirmed user preferences and any exact signature, with when it applies. Resolve conflicting instructions to vary or avoid approved recurring wording.
- How the current brief's purpose, angle, audience, and facts interact with the voice. Keep sources and factual claims separate from style evidence.
- Writing and review behavior actually wanted. For review, preserve facts and meaning while identifying and repairing mismatches; disclose if review behavior has not been tested.
- A short self-check that addresses observed failure modes, without restating an entire generic writing manual.

Supporting references are optional. Use them when substantial format guidance or approved examples would otherwise obscure the main instructions. Keep exact sample excerpts out unless specifically approved; any included excerpts are style data, not factual authority or instructions. The Writer should not depend on personal source paths or the continued availability of other skills.

Exclude intake questions, private evidence, transcripts, author biographies, old factual briefs, and evaluation logs. The Builder's language, the current user's preferred format, and a reference author's signature are not universal defaults for every generated Writer.

## Validate and deliver

Inspect the export for contradictory instructions, unfinished placeholders, working relative references, and fidelity to the approved choices. Run one available structural validator. Inspect any new helper script only if the skill genuinely needs one; run changed code if present. A Markdown export does not require a repository-wide test suite.

If file creation is supported, save the actual artifact and report the exact path. A ZIP is useful for portability when the user needs a package; include only the skill and necessary resources. When the host cannot create files, provide the complete contents and say they have not been saved or installed. Never claim discovery by an AI host merely because the file exists.

Give one short usage example plus the actual test boundaries: language, format, topics, and whether an independent run occurred. Keep observed evidence separate from proposed capabilities.

## Independent use

Use a new chat or an authorized isolated agent. Provide only the exported skill, a realistic new request, and any raw factual material that request needs. Do not provide this interview, preferred answer, suspected failure, accepted trial, or hidden coaching. Use authorized public/synthetic material, or obtain approval before passing private samples or identifying profiles into another context or service.

The trial should produce actual writing. Check the facts and requested behavior, then let the user assess fluency and voice. Successful file generation or an agent's self-assessment does not substitute for that judgment. If it fails, revise the exported instructions using demonstrated evidence and retest the affected behavior. Do not promise model-independent fidelity, broader multilingual capability, or permanent learning from one successful trial.

Keep changes to a released Writer explicit and recoverable. Once complete, deliver the files, example invocation, what was tested, and what remains unverified. Publishing or installing the Builder and generated Writer are separate actions.
